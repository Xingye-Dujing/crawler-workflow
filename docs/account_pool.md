# 账号池与出口池（IP 池）

平台账号被管控往往不是几分钟的事。这个功能的重点是**记住哪一组登录与出口已经被拦过、到什么时候**，
让下一次运行直接跳过它，而不是把同一堵墙再撞一遍。轮换只是这个记忆的下游动作。

## 实体与状态

- **账号** = 一份已保存的 Cookie（`data/<账号树>/cookies/<平台>@<账号>_cookies.json`），不另建清单。
- **出口** = 一条代理（`http` / `https` / `socks5`，可选用户名密码），可以限定适用平台。
- **绑定** = 某个 `(平台, 账号)` 固定从哪个出口出去。**粘性**：同一个登录在两次请求之间换国家本身就是风控信号；
  只有出口被冷却时才换出口，且仍然用同一个登录（“换 IP 不换号”）。
- **健康** = 每一条 `(account|exit, 平台, 主体)` 的状态：`ok` / `cooling`（到某个时刻）/ `disabled`（人工停用）。

持久化在账号树里的 `data/pool.db`（托管模式下 `data/users/<id>/pool.db`），所以重启之后冷却依然有效；
读取时用当前时间比较 `cool_until`，到点自动回到 `ok`，不需要后台线程。

## 失败归因：只冷却有证据的一方

| 失败信号 | 冷却账号 | 冷却出口 | 理由 |
|---|---|---|---|
| `login_wall` | `pool_cooldown_seconds`（默认 7200） | 不冷却 | 会话死了，出口通常无罪 |
| `risk_blocked`（验证码/风控） | 先 10 分钟；同一账号再次风控则全程 | `pool_cooldown_seconds` | 风控首先怀疑出口 |
| `unreachable` / 网络报错 | 不冷却 | `pool_network_cooldown_seconds`（默认 300） | 机器或线路问题，不是账号问题 |
| 采得不足、0 行、普通超时 | 不冷却 | 不冷却 | 没有证据，冷却谁都是猜 |
| 用户停止 | 不冷却 | 不冷却 | 立刻结束，不再开浏览器 |

**未知就是未知**：预检的 `unknown` 与这里的“不冷却”是同一条规则的两面。

## 轮换只在一个安全点发生

- **数据源节点**：只在**本次尝试零行**且失败是 `login_wall` / `risk_blocked` 时换下一组。
  已经有行落库时走既有的“保留行、结算 PARTIAL、继续”路径——换号会让账本、游标与“采得不足”的判定同时变复杂，
  而收益主要落在“一进门就被拦”的场景。`SessionBlockedError` 就是这一步的专用信号（`crawlers/core/faults.py`）。
- **评论节点**：按链接换号。当前链接被拦 → 冷却 → 丢掉该平台的会话 → 用下一组**重走同一条链接**。
  `url_index` 只记“已证明的连续前缀”，这条链接本来就没有被证明，所以游标不需要动。
- **每次尝试重新拿 `gate.hold(..., account=该次真实账号)`**：lane 是按账号分的，用哨兵 `@pool` 拿 lane 会把
  一个平台的池内并行串成一条队。
- **上限**：`pool_max_attempts`（默认 3）。用完就抛一条按名字列出每个账号与冷却时间的拒绝，
  而不是“Cookie 已失效”这种把人送去重登的错误建议。
- **池模式跳过同账号退避重试**（`pool_skip_wall_backoff`，默认开）：刚测出来的墙，再撞一次正是这个功能要避免的花费。
- **CatBus 不参与**：它的登录在自己的账号目录里，`@pool` 对它按名拒绝。

## 预检与运行前门禁

- 冷却中的账号**不开浏览器**，直接按台账回答 `cooling`（阻塞）。
- 池节点按**池**回答：只要还有一个可用的 `(账号, 出口)` 就不拦；全部冷却/未保存登录才拦，并区分
  “池里没有登录”和“现在全在冷却”。
- 默认只读状态（`pool_preflight_live` 关）；打开后才会真的用第一个候选验证一次，并把结果写回台账。
- 保存/重取 Cookie 是**新的会话**：清掉该账号的冷却与 strikes，并让预检缓存失效。手动“解冻/验证”同理。

## 出口（代理）接入

- 无认证出口：`--proxy-server=http://host:port` + `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`
  （后者堵住 WebRTC 用 UDP 泄漏本机地址）。
- 有认证的 HTTP 出口：`crawlers/core/proxy.py` 起一个只监听 `127.0.0.1` 的 CONNECT 中继，由它给上游加
  `Proxy-Authorization`。凭据**不进浏览器 argv、不进日志**；中继与 driver 同生共死。
  带认证的 SOCKS5 明确按名拒绝（不做一半的 SOCKS5 握手）。
- 出口解析收敛在 `crawlers/__init__.py::get_crawler`：采集、登录窗口、验证、预检四条路走同一个出口——
  在 A 出口登录、在 B 出口采集本身就是风控诱因。
- 出口全部冷却且 `pool_allow_direct_fallback` 关（默认）时，宁可拒绝也不直连：直连会暴露代理想藏起来的地址。
- 凭据只存在 `pool.db`，接口只回 `has_auth`；面板与日志只能看到名称和 `host:port`。

## 边界与不变量

- **一个节点一份账本、一个游标**：换号不移动 `item:` 作用域，也不让游标越过没证明的空洞。
- **指纹**：`account='@pool'` 原样进指纹（池模式与固定账号是两次不同的采集）；`@` 不是合法账号字符，
  所以它永远不会和用户自己起的账号名撞车，也永远不能被交给 `CookieManager.path_for`。
- **前端不做判断**：状态、冷却时间、可用数量全部由 `/api/pool/state` 给出；面板只格式化。
- 出口、账号的增删改在托管模式下限管理员；读取对当前登录账号开放。

## 面板

Cookie 底栏的三个页签：**账号**（原有表格 + 状态 / 冷却至 / 出口 / 解冻 / 停用）、**出口**（清单、表单、批量导入）、
**最近记录**（每次成功/失败、账号、出口、行数、运行 id）。功能关掉时底栏与原来完全一致。

## 配置

`pool_enabled`、`pool_cooldown_seconds`、`pool_network_cooldown_seconds`、`pool_max_attempts`、`pool_escalate`、
`pool_allow_direct_fallback`、`pool_skip_wall_backoff`、`pool_preflight_live`。逐项说明见
[config.md](config.md)。
