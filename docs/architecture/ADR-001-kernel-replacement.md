# ADR-001：内核替换，而不是推倒重来

- 状态：已接受（2026-11-22）
- 决策者：项目所有者 + 架构实施
- 相关：[ADR-002](ADR-002-capability-manifest.md)、[ADR-003](ADR-003-durable-state.md)

## 背景

采析绘已经有可运行的产品面：9 个采集平台、16 个节点、38 个分析算子、30 个图表、断点续跑、账号与出口池、三系统打包，以及约 10.6k 条快速测试。扩展点的痛点不在业务实现本身，而在“同一事实被复制到十几处”：节点类型、默认参数、前端表单、验证、AI 词汇/工具/技能、测试矩阵、文档各自维护一份。

用户要求“架构级重写/重构，新增内容只改一处，其它自动生成或门禁报错”。如果按字面“全部从头再来”，会把已经验证过的采集/分析/断点续跑同时置于风险中，且无法在每一步保持可运行。

## 决策

采用**内核替换 + 逐域迁移**（strangler pattern）：

- 保留：`crawlers/`、`analyzers/`、`services/` 的业务实现，`services/runs/store` 的断点语义，平台/账号/安全规则。
- 替换：扩展点（manifest + registry）、验证（单引擎）、AI 知识/工具（能力生成）、前端节点 UI（schema 驱动）、测试矩阵（生成式）。
- 每个域一次迁移，旧路径用 `runtime/flags.py` 的迁移开关并存；parity 绿后删旧路径。
- 不做“大爆炸”删除；任何阶段都必须可运行、可回滚、可验收。

## 为什么不是全量重写

- 业务实现已经承载了大量真实站点与真实数据的经验（风控、登录墙、分页、断点、去重、图表契约），重写会把这些经验变成“再踩一次”。
- 用户的核心诉求是**可扩展性**，不是“代码更新”。可扩展性来自契约与派生，不来自把文件换个目录。
- 逐域迁移能每一步量化收益（新增节点只改一处、验证不再双写、技能自动生成），全量重写只能到最后一天才知道有没有退步。

## 后果

- 短期内会有“旧路径 + 新路径”并存，必须用开关和 parity matrix 管理；开关有 owner 与移除日期，过期门禁失败。
- 每个域迁移前必须先写“扩展剧本”和“完整性门禁”，否则迁移会变成第二次复制。
- 旧路径的 bug 只在“数据丢失/安全”级别做热修；其余等新路径一次性解决，避免在将被删除的代码上重复投入。

## 被否决的替代方案

- **推倒重来**：风险与周期不可控；现有测试是资产，不是包袱。
- **只加测试，不改架构**：测试只能发现漏配，不能消除“同一事实十几处”的根因。
- **引入重型框架（Django/React/完整工作流引擎）**：与零构建、本地优先、三系统打包的约束冲突；需要的是契约，不是运行时。
